pg_tokenizer 1.3.0 reduces the cost of repeated primary reads, custom vocabulary writes and conversion to PostgreSQL `tsvector`. It supports PostgreSQL 15–19 on x86_64 and aarch64.

## Highlights

- **Definition caches.** On an up-to-date primary, repeated reads can reuse a validated cache without SPI calls, extension membership lookups or marking the command ID as used. Statement triggers mark local changes before row processing and publish successful definition changes. Old snapshots, physical standbys, promotion and databases still running 1.2.0 SQL use the snapshot-visible definition version. Unrelated rollbacks preserve validated models and analyzers on the primary.
- **Custom vocabulary.** Writers check distinct candidate terms through parameterized queries that can use the existing unique index. Known terms consume no new IDs. The model's transaction advisory lock serializes concurrent new-term insertion and the two independent triggers continue to evaluate their own row predicates. Ordinary tokenization reads the caller's snapshot. Target assignments honor PostgreSQL casts and the privileges and settings of the SQL `tokenize` function.
- **Native binary `TSVector` builders.** `analyze_to_tsvector` and `tokenize_to_tsvector` are now native `LANGUAGE c` functions that construct PostgreSQL `TSVectorData` varlenas directly, skipping SQL wrapper invocation, text escaping, `int4[]::text[]` casts, and `tsvectorin` reparsing while preserving identical lexeme sorting, 2,046-byte limit, 256-position cap, 16,383 position clamp, and 1,048,575-byte `MAXSTRPOS` enforcement. `_tokens_to_tsvector_text` and `_analyze_to_tsvector_text` remain exported for backward compatibility.
- **Streamlined analysis and tokenization pipeline.** Pipeline calls read GUC budget limits once, eliminate intermediate `Vec<&str>` and redundant post-stage budget passes, avoid `String` copies on empty/identity analyzers, fuse `Vec<i32>` output directly, throttle lightweight filter interrupt checks to every 1,024 tokens, make non-ASCII `to_lowercase` single-pass (zero-allocation for unchanged CJK while preserving Greek final sigma), add an ASCII zero-allocation fast path to Unicode normalization (`nfc`/`nfd`/`nfkc`/`nfkd`), optimize `ngram` batches (ASCII fast path + reusable offset scratch), and remove per-token temporary vectors and `CString` allocations in `pg_dict`.
- **Hugging Face `padding.pad_id` validation.** `create_huggingface_model` now also checks `padding.pad_id <= 2147483647` at import time in addition to vocabulary, added tokens, and post-processor special tokens.
- **Package verification.** The raw pgrx package, ZIP and Debian package include the 1.2.0 upgrade script. CI checks the installed migrations against the release sources before adding historical install scripts for upgrade tests.

## Packages and Upgrading

The Linux DEB dependency and the ZIP's `pg_tokenizer.control` record the minimum server version required by the linked PostgreSQL tuple-header functions. Check this before restarting a server with the new library. [Binary installation](../01-installation.md)

- **In-place 1.2.0 → 1.3.0 upgrade.** Install the `1.3.0` shared library and SQL files, restart PostgreSQL, and run `ALTER EXTENSION pg_tokenizer UPDATE;` in each database. Existing catalog definitions, custom vocabulary IDs, views, and triggers are preserved in place. Backends running the `1.3.0` binary against un-upgraded `1.2.0` SQL continue to work safely on the `definition_version` path until `ALTER EXTENSION pg_tokenizer UPDATE;` runs.
- **Operational note on trigger bypass.** See [Backend-Local Definition Caches](../07-limitation.md#backend-local-definition-caches) for the documented recovery step if a superuser modifies `tokenizer_catalog` tables with triggers disabled or under `session_replication_role = replica`.
